## 3. 必须保持的安全不变量

1. 围栏记录（`fence/intent.json`、`fence/exclusive.json`）必须**原子写**（temp + fsync + rename）且**严格读**：解析失败必须 `MIGRATION_FENCE_{INTENT,EXCLUSIVE}_UNREADABLE` fail-closed，**不得**回退成"没有维护态"。
2. 同一 `operationId` 同一时刻只允许一个 owner：`ownerToken` 参与 `verify()` / `release()`；同 id 的存活他 owner → `MIGRATION_FENCE_OWNER_CONFLICT`；被接管的句柄 → `MIGRATION_FENCE_OWNER_LOST`。死 owner 接管语义不变。
3. `abandonMigrationIntent` 是 drain 超时后**唯一**合法出口，必须带显式证据并先写 `fence/abandoned-intents.jsonl` 审计；任何 exclusive 记录（含残渣）一律拒绝；坏 intent **故意不可撤回**（需人工看字节）。它**不是** `release()` 的替代，`release()` 前置未被放宽。
4. 编排层：**journal 是决策权威，fence 文件只是动作句柄**；`release` 必须重算四硬前提（drain-completed / capture 重算校验 / gate 到 `rolled-back` 且 `recognized` / owner 一致），任一不满足即 `blocked-release` 且**保留 intent**。取消不是回滚。
5. `activationSupported`、`postActivationRollbackSupported`、`stopWriteProvable` 恒为 false；**不存在 `activate → committed` 路径**；默认 verifier 恒拒绝，C1–C10 全 false。
6. 锁序唯一允许 **fence → commit**（`migration-gate.lock`），禁止反向；未持有已验证 exclusive 时不得进 maintenance。
7. 编排模块**不接线产品入口**（`.dsh-plugin/*` 零引用），因此它不证明产品迁移能力。
8. 不绕过授权、无原生 shell 回退、不放宽模型面；产品验证保持 0 真实模型推理，禁止随手跑 `scripts/integration-cli-runtime.mjs`。

## 5. 失败、修复与环境记录（不改写成一次通过）

1. **G1/G2/G4 是既有缺口，本轮才闭合**：`beginMigrationExclusive` 原来直接 `writeFile`（非原子）、`readJson` 把坏 JSON 当 `null` 而准入判断据此放行新 writer；同 `operationId` 重入不校验 owner（可"双双持有"）；drain 超时后 `release()` 必然 `MIGRATION_FENCE_NOT_HELD`，只能人肉删文件。三处均给了反向对照实验（把修复还原即复现漏洞）。
2. **设计文档链接逃出 `plan/`**：初版第 5 行 `](../HANDOFF-*.md)` 让 `integration-documents` 失败（`link stays in source bundle`）。这是**我方的全量根回归**抓到的，子代理只跑 6 个文件扫不到。已改为反引号代码路径。
3. **测试侧等待竞态**：`tests/fixtures/migration-fence-holder.mjs` 只写 `'ACQUIRED'` / 错误码（永不写空串），而旧 `waitFile` 只要 `readFile` 成功就返回——`writeFile` 先建空文件再落字节，于是读到 `''` 被当成答案。全量回归两次各命中一次（`a crashed coordinator…` / `a host arriving after the intent…`）。已改为"等到 trim 后非空"，超时/轮询/断言/用例条数均未变；**35 次连跑 0 失败**（15 串行 + 20 并发）。**这不是产品缺陷，也不是本切片引入。**
4. **Windows rename EPERM（既有，未修）**：`migration-configuration-commit.mjs` 的 `atomicJson` 在 `temp → migration-gate.json` 的 rename 上被 Windows 拒绝，本机命中率约 **1/5~1/6**（高竞争、24 个崩溃注入子进程反复重写同一 gate）。失败是 **fail-closed**（卡住而非写坏），但**不可自愈**。建议下一项小改动：对 `rename` 加有界重试（仅 `EPERM/EACCES/EBUSY`，如 5 × 50ms），fence 的 `atomicJson` 同模式同风险。**本轮按边界未动产品代码。**
5. **一次自我更正**：我曾判定子代理"61 tests / 60 pass"是算错；核实后是**两个不同组合**——61 是「五套迁移 + rollback-readiness(6)」，60 是「五套迁移 + ci-contract(5)」，两者都真实。台账已改写为"两种组合都实测、都正确"，并保留我这次误判。
