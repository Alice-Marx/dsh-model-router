# 自行实测：安装验收与模型路由质量—成本实验

日期：2026-10-04。状态：实验方案，真实实验尚未执行。本方案不再等待最新 LiveBench 逐题文件；可以使用你自己新编、具有使用授权的题目，名称写“自建题集”，不要称为官方 LiveBench 最新成绩。

费用口径按用户补充调整：主实验采用各供应商官方计费规则与实际 usage 计算成本（`usage-priced`），不要求账单或实际扣费金额作为开测/统计前提。账单只作可选交叉核验；以下“成本”默认指这一官方定价核算口径。

## 先知道哪些需要你测

| 层次 | 需要实际验证的内容 | 是否调用模型 | 能得到的结论 |
| --- | --- | --- | --- |
| A：桌面验收，先做 | 本地安装、UI 排版、配置保存、预览失效、预算提示、真实执行路线 | 大部分不需要；最后做少量调用 | 本机宿主是否可用，不证明选模更优 |
| B：同题矩阵，主要实验 | 每题让每个候选模型作答、盲评、记录费用，比较冻结的新旧选择 | 需要 | 固定生成设置下的模型选择投影，是否质量不降且成本下降 |
| C：完整团队，B 后选做 | 带依赖的实际工作包、汇总、改派、失败/重试、总账 | 需要，可能较多 | 真正端到端团队效果；不能由 B 直接推得 |

已有单元测试、合成求解实验和 UI 模拟预览是工程证据；不需要你手工重复每条单测，但要在自己的环境重跑。真实收益、供应商实际模型身份、费用、延迟和宿主交互仍需实测。

重要边界：`buildPlan().selected` 是计划首包选择，复杂题首包可能是分析；`mode: single` 也不保证只有一个节点。当前推荐的 reasoning effort 尚未完整传入执行链。本轮 B 只测 **provider/model 选择投影**，不能宣称同时验证了 effort 优化或 DAG。

使用独立测试 profile；备份原 profile/state，不覆盖日常数据。旧新版插件 ID 相同，不在同一 profile 同时启用。记录 Harness 版本、Windows 版本、插件包 SHA-256、源码 dirty 状态；不只写开发版本号。

## 步骤 2：先冻结方案，不看结果挑规则

复制配套文件到自己新建的实验目录，保留原模板：

- `docs/experiments/20261004-selftest/protocol.template.json`：预算、模型动作与比较规则。
- `docs/experiments/20261004-selftest/replay-input.template.json`：仅含题目与冻结 planner 输入。
- `docs/experiments/20261004-selftest/paired-input.template.json`：后续连接真实结果的统计输入。

模板中的待填 `null`、空模型/结果数组和 `TODO` 必须补全，不是实验数据；有明确关闭语义的 `liveBench: null` 则应保留。正式测试前将协议设为 `frozen` 并保存 SHA-256；以后改规则必须另立实验 ID。

固定 3 个你当前确实可调用的模型（低价、中档、高质量各一个即可；不可根据 test 成绩挑模型池）。每个动作记录精确 provider/model、版本/日期、API 或 CLI 通道、实际 effort、system prompt、解码参数、输出 cap、超时、重试/降级规则。某参数不支持就注明，不能假称三家行为完全一致。

先只做文字直接回答、禁工具和联网，避免把工具能力混进选模比较。一个模型固定一种实际生成设置；两版共享同一动作池、路由档案、价格和可用性。不要拿高 effort 答案去支持低 effort 的选择。

初次 B 推荐 `preset: balanced`、`mode: single`、`liveBench: null`，冻结目录顺序与外部画像；`budgetUsd: 0` 表示 planner 不设预算约束，**不表示免费调用**。另在协议中设置实际采集金额上限，最好同步设置供应商端限额。本轮不证明同预算 DAG 优化；预算敏感性另立实验。

预先登记主比较家族（K=3）：

1. 当前源码 `current-balanced` vs 0.15.0 `old-balanced`。
2. 当前源码 vs 验证集选出的最佳固定单模型 `validation-best-single`。
3. 当前源码 vs 验证集分领域固定单模型 `validation-domain-single-diagnostic`；这是依赖已知题目领域的诊断基线，不直接视为可部署路由器。

主指标：逐题 `quality ∈ [0,1]` 的 micro 均值、逐题同口径 USD 成本。默认质量非劣界限为 0；若业务允许下降，必须在 test 前写明具体界限，不能看结果后放宽。macro/逐领域质量、失败率、延迟 p50/p95、截断率和实际预算超限率一并报告。

## 步骤 3：先做小样，确认采集可行再扩大

小样建议 **18 题 × 3 模型 × 1 次 = 54 次模型调用**：6 个领域各 3 题，例如数学、推理、代码、信息抽取、摘要、指令遵循。它用于检查评分、日志、费用和 cap，不用于宣布正式收益。18 题不是统计充分样本。

小样只检查采集链，可以不运行正式比较统计；不从小样成绩推导 test 收益。54 次不包含 A 的冒烟调用、重试和收费裁判，应另计总预算。

自己写新题或用有授权的材料；客观题先写答案/测试，主观题先写 rubric。避免私密资料，不执行模型给出的未知危险代码。先估算 54 次调用与可能重试、评分器的研究总费用，写好金额上限后才采集；超过上限或出现身份/计费异常就暂停，不能靠无休止重试完成矩阵。

小样完成后确定正式样本规模。一个可调整的工作量示例是 **600 题 × 3 模型 × 1 次 = 1800 次调用**，并非已经做过功效分析，也不保证显著。按小样的成对差异、独立题组数和预算重新规划；预算小就报告探索性研究，不承诺收益成立。费用预算包括 train/validation/test 所有调用、失败尝试和评分；后续若增加重复次数，调用量同比增加。

小样题及同材料/近重复模板族不进入正式 test，不能只换措辞或ID就当新测试。正式题目相似改写/同材料题设为同一 `groupId`，重复生成同题也不当作独立样本。跨领域重复题先归并到同一规范领域。

在采集结果前按组划分：`SHA256('dsh-selftest-v1:' + groupId)` 取前 8 个十六进制字符转整数、模 100；0–59 为 train，60–79 为 validation，80–99 为 test。比例约 60/20/20，实际数不必刚好 360/120/120。保存题目清单、split、prompt hash 与评分规则，不能为了结果好看重新分组/划分。

正式 train/validation/test 均须非空；若初始划分为空，先在未查看test结果时补充独立新题组并更新预登记规模，不改salt挑好分组。各领域独立组过少时只能探索性报告，不能用几百条同材料改写伪装大样本。

## 步骤 4：每一题让全部候选作答，保存完整记录

同题给所有候选相同可见输入和输出任务，生成设置按步骤 2 固定。模型调用顺序随机交错，记录时间区间，避免一个模型全在高峰期。采集可以用你已有 API/CLI 或手工执行；**当前项目没有通用矩阵采集器和自动评分器**，以下字段需要你保存，不能把模板当采集结果。

正式阶段先采集/评分 train 和 validation，完成步骤 5 的画像/基线冻结及步骤 6 的 test 选择封存后，再采集和评分 test。若提前采集了 test，结果与评分必须由独立人员/存储封存，调参者不可查看。这里的步骤 4–6 分阶段执行，不是先看完全部题目成绩再选规则。

每次尝试至少记录：

- 题目：`id / groupId / domain / split / 完整 prompt / promptSha256 / 题集日期`。
- 动作：实际 provider/model/version/effort、完整生成设置、通道、请求或响应 ID、时间戳。
- 原始结果：完整回答、错误类型、每次重试/降级、输出是否截断、耗时；可用时保存 TTFT。
- 用量与费用：输入/输出/缓存/推理 token 的厂商原字段、每次尝试金额、币种、计费来源与价格生效日期。
- 评分：quality、评分规则/评分器版本、评分理由与盲评标识。

不要只依赖插件历史：任务和回答摘录会截断，无法替代完整实验原文。原始响应另存，只分享脱敏副本。

主实验的 `costBasis` 使用 `usage-priced`：按每个具体模型/供应商的官方价格与计费说明，乘以实际返回的 usage，得到可复算的官方定价成本。无需等待账单；`invoiced` 只用于你愿意另做的实际扣费核验。官方价核算不是账户折扣、赠额、订阅或中转商的实际扣款，报告将两者区分即可，不因此阻止实验。

### 官方计费成本怎么计算

1. 选定动作后，为每个精确 provider/model/版本/接口保存官方价格页与 usage 字段说明、查阅日期、生效时间、原币种及计量单位。记录服务档、上下文长度档、缓存TTL、批量/实时模式以及适用的时段规则；不把同名模型不同通道的价格混用。
2. 将原始 usage 按官方说明拆成不重叠的计费项，再用对应费率。通用记账形式是 `单次成本 = Σ(该计费项实际用量 × 单价 ÷ 该单价对应的计量单位) + 适用非token收费`；只有全部单价都按百万token时，才统一除以 `1,000,000`。这不是要求所有供应商使用同一种输入字段。
3. 缓存读、不同TTL缓存写、普通输入、输出分别按文档计费；总输入字段若已包括缓存，不能整段按普通输入价格计一次后再加缓存费。推理token若已含在计费输出总数中，不能再加一次。原字段保存不变，另外记录你的映射和计算过程。
4. 对每次实际尝试单独计算并相加，计入可确认的失败/重试、工具等费用。重试次数不等于每次都一定收费；应以厂商计费规则和真实用量为准。没有usage或关键计费项时保持未知，不按字符数、任务预算或可见回答长度伪造实际token，也不能填0。
5. 冻结的是价目表和计算规则版本，不是把不同长度档/时段硬塞成一个费率。跨价格变更时逐次记录当时费率；若另外用统一日期价目表重算，标明为统一价反事实成本，不冒充历史实际费用。原币非USD时保存换算来源/日期，不混加币种。

规则核对示例（2026-10-04，未替你指定候选模型或填价格）：[DeepSeek官方价目表](https://api-docs.deepseek.com/quick_start/pricing/)区分缓存命中/未命中与适用时段；[Claude缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)区分普通输入、缓存读与缓存写的usage；[Claude推理计费说明](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost)明确计费输出总数包含推理token。这些示例说明应逐供应商映射，不代表所有模型已经完成价格登记。

直连API按该供应商官方规则核算；若你选择订阅CLI或中转通道，却统一采用原厂API价格做比较，标为“官方标准API等价成本”，不要称为该通道实际扣费。CLI未提供完整usage时，改用能记录真实usage的采集通道或补齐日志。插件规划的 estimatedSavings 仍不是实测成本。

提前固定失败规则：超时/拒答等导致无可用答案，可在“运营质量”指标记 0，但必须保留尝试和费用。缺日志、没采集到或费用未知属于缺数据，不冒充答错/免费。截断回答按冻结规则评分，不自动丢弃。任何排除都报告数量与覆盖，禁止根据“这题新版选错/更贵”删题；无法形成完整成本矩阵时先报告缺失，不能宣布完整收益。

## 步骤 5：盲评，再用 train/validation 冻结画像和基线

数学/抽取按答案，代码按隔离环境中的测试，摘要/指令按先写的 rubric。主观评分隐藏模型名、版本和成本，随机回答顺序；可以用双人评分并处理分歧。若用模型裁判，冻结裁判模型/提示词，并人工抽查；评分器费用记入研究预算，不冒充路由执行费用。

quality 直接保留 `[0,1]` 部分分，不能 `Boolean(score)`。验证回答的是同一个 prompt、动作设置与 cap；不同提示词实验必须分开。每题全部候选均有原始回答、评分和同口径成本才进入完整矩阵核验。

train 仅用于建立模型质量/专长等档案；无新学习器时不声称完成概率校准。两版使用相同冻结画像，不能新版用真实 train、旧版用默认弱画像。validation 选择最佳固定单模型及分领域单模型：最高平均质量，平手按较低平均成本，再按稳定动作 ID；某领域 validation 没有完整有效题时，预登记回退到全局 validation-best-single，并报告覆盖。若全局也没有完整有效题则暂停，不用 test 选基线。test 不能参与此选择。若以后学习策略或调参，也只能用 train/validation。

单价、latency/risk、目录和 LiveBench 输入也冻结；没有依据的风险/延迟保持“未测”标记，路由器缺省代理值不能当实测结果，不把 test 标签换成“任务质量分”。将每题原文和同一个 plannerInput 写入独立 `replay-input.json`，这个文件不能含答案、评分或结果字段。

`plannerInput.available` 每项用宿主准确的 `provider`、`model`；`quality` 为该模型 train 分的 `[0,1]` 均值，`qualityBias` 设 0，`pricing` 的 input/output/cacheRead/cacheWrite 为 USD/百万 token。实际支持可控 effort 时，`reasoningEfforts` 只放本轮固定的那个 ID，`defaultReasoningEffort` 同值；否则注明供应商默认/不可控。latency/risk 是归一化代理而不是毫秒/错误率，若加入必须事先定义变换；不可直接填毫秒数。另保存每个字段的 train/价格来源。不要依赖内置目录的历史模型质量和价格作为本次真实证据。

## 步骤 6：离线生成两版选择，先存 hash 再连接 test 结果

本次配套增加了两个小型离线入口，只在 Git 源码仓库中使用；不会调用模型。正式 `replay-input.json` 的 queries 仅放冻结划分中的 test 题，题目ID逐一对照split清单，不混入train/validation/小样；探索性回放另存。旧版基线目录已存在，但使用前仍需核对：

```powershell
git -C .\test-artifacts\github-0.15.0-checkout rev-parse HEAD
node .\docs\experiments\20261004-selftest\replay-choices.mjs --help
node .\docs\experiments\20261004-selftest\replay-choices.mjs .\my-experiment\replay-input.json .\test-artifacts\github-0.15.0-checkout | Out-File -Encoding utf8 .\my-experiment\choices.json
Get-FileHash -Algorithm SHA256 .\my-experiment\choices.json
```

基线应为 `aca9912921aee50858e4b95c8698e3177e22335c`；若目录缺失或 commit 不符，先核对来源，不用别的版本冒充。当前 dirty 源码由辅助入口记录 shared `.mjs` hash，另保存 `git status --short`。保存两版完整 plan、首选 provider/model、节点数和输入 hash；plan 的 generatedAt 不用于选择一致性比较。

此入口只把两版 `plan.selected` 投影到固定模型池。空选择、池外选择、不同 effort/cap 或无法匹配的动作必须报告；不能事后换成该题最高分模型。补充分析若只看“两版都恰有一个 execution 节点”的题，必须依据 query/plan 定义资格并报告覆盖，不能假称所有 single 计划都是这种情况。

确认选择文件封存后，按步骤 4–5 的冻结采集/评分规则取得 test 矩阵，再按精确题目+动作连接真实 test quality/cost，生成 `paired-input.json`：每行有相同 `id/groupId/domain`，outcomes 包含四个策略的 quality/costUsd。策略成本是选中动作由真实usage按冻结官方规则计算的成本，加预先约定的路由开销；无需账单，未知用量/费用不能填零。本地无供应商调用的 planner 可记供应商路由费 0，CPU时间另记，不能一概把其他开销记 0。

做泄漏自检：保持 query-only 输入不变，仅在外部结果副本中打乱标签、将 test 成本乘 10，再运行选择；去掉 generatedAt 后选择必须不变。辅助入口拒绝题目中的结果字段，但仍需人工核对画像确实来自 train。

注意：为了采集矩阵，你实际上支付了全部模型调用费用。按某个策略选中单元格得到的是“固定直接回答实验下的回放成本”，不等于这次研究账单已经省钱，也不是完整生产 DAG 成本。

## 步骤 7：算配对统计，按预先规则判断

先在 `protocol.json` 写好并冻结比较家族与统计设置；把选择文件 hash 填入 paired 输入，未知成本保持缺失并先解决数据核验。配套入口支持连续分：

```powershell
node .\docs\experiments\20261004-selftest\analyze-paired.mjs --help
node .\docs\experiments\20261004-selftest\analyze-paired.mjs .\my-experiment\paired-input.json .\my-experiment\protocol.json | Out-File -Encoding utf8 .\my-experiment\paired-report.json
```

默认 seed=20261003，4000 次、领域内整组配对 bootstrap，alpha=0.05，K 取完整比较家族数。质量差为“新−基线”，成本差也为“新−基线”；节省比例为 `1 − mean(Cnew)/mean(Cbase)`，不是逐题节省率平均。

正式 `paired-input.json` 的 stage 为 `test`，rows 只含冻结划分中的 test 题，不混入 train/validation/小样；辅助入口只校验字段，split 成员身份仍需和封存清单核对。

每个比较只有同时满足以下条件才有“质量不降且成本下降”的近似统计支持：

1. 经比较家族校正的一侧质量下界 ≥ 负的预登记非劣界限，并通过补偿计算的边界检查。
2. 一侧成本差上界严格低于公开数值容差的负值。

“没有显著变差”不等于非劣成立；某一对通过不代表三对都通过。样本少或每领域只有一个独立组时不宣布可靠结论。bootstrap 是近似推断，不是有限样本风险认证；辅助工具不能自动认证原始数据真实性、组独立性或 test 没被偷看。

以 `usage-priced` 作为主成本轴即可检验“在官方计费口径下，质量不降且成本下降”，不用等账单；结论写清所用规则/日期。只有另外声称账户实际扣费节省，才需要对应扣费证据。没有通过时写“证据不足/质量下降/费用未下降”，不要自动调规则重测同一 test。最佳便宜单模型、随机和事后 Oracle 可作描述性补充，Oracle 不可部署；增加正式比较时必须事先扩充 K。

现有 `node scripts/evaluate-routing.mjs <dataset.json>` 是另一个二元 `correct:boolean` 描述工具，依赖外部提供的 selected，不采集、不生成双版本选择。连续分实验使用本步骤入口，不把部分分硬转布尔。

## 步骤 8：B 后再单独做 C，最后形成报告

若要验证用户真正感受到的“团队更好/更省”，另立协议，使用新任务：先做 4 个工作流排障，再按预算扩至例如 20 个。旧新版本的最终交付标准相同，固定运行环境、权限、工具/模型池、可见文件、预算和超时；运行顺序交错，每次从等价的独立输入工作区开始。具体样本与重复数仍须规划，不沿用 B 的显著性结论。

保存实际执行 plan 与每个工作包上下文、实际模型/设置、依赖答案、汇总、重试/降级、工具/复核调用、完整最终结果和累计总成本。执行入口可能重新规划，不能只保存 UI 初次预览。对最终成果盲评，与实际总账成对比较，同时报告工作流成功率和耗时；订阅/API账分开。

没有实际观测到 effort 被传入并生效时，写“未验证/实现缺口”；若要实验 model×effort 联合策略，先补齐执行链并采集各动作矩阵，另立方案。本指南不自动修复该实现缺口。

最后交回：冻结协议、题目与分组划分、动作设置、脱敏原始响应、逐题评分与费用、两版选择/完整 plan、hash manifest、配对报告、UI验收记录、失败/缺失/覆盖表。研究总花费和策略回放费用分别列出；结论限定到本次题集、日期、动作池与执行协议，不外推所有模型或未来版本。

第一轮建议只完成 A 与 54 次小样。记录可靠、金额可接受后，再决定正式规模；目前没有进行真实采集，也没有验证真实收益。
